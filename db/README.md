# قاعدة بيانات خرسانة برو: إرشادات الأمان والتشغيل

## الحالة
هذه **ملفات هيكل قاعدة بيانات فقط**. لم تُنشأ قاعدة بيانات سحابية، ولم تُطبّق الهجرة بعد، ولم يتم ربط الموقع بها. لا تدخل بيانات حقيقية قبل اكتمال المراجعة والتشغيل الآمن.

## التصميم الأولي
- `factories`: الكيان المستقل لكل مصنع.
- `factory_members`: عضويات المصنع ودور المستخدم.
- `orders`, `suppliers`, `purchase_requests`, `expenses`: سجلات مرتبطة بعمود `factory_id`.
- `audit_events`: سجل التدقيق (يتطلب خدمة كتابة وتدقيق إضافية قبل الإنتاج).
- سياسات Row Level Security (RLS): القراءة حسب عضوية المصنع، والكتابة حسب الدور.
- لا توجد أي سياسة تسمح للمستخدم بإضافة نفسه إلى مصنع أو ترقية صلاحياته.

## متطلبات الإنتاج (حاجز إلزامي)
1. إنشاء مشروع Supabase منفصل للتجربة ثم إعداد إدارة مفاتيح وأسرار آمنة على الخادم؛ يمنع وضع service-role في المتصفح.
2. إنشاء Endpoints مصادقة آمنة وعمليات دعوة للأعضاء وتأسيس مصانع، مع التحقق من الصلاحيات وإثبات ملكية المصنع.
3. تنفيذ معاملات مالية داخل قاعدة البيانات (transaction)، وتوثيق الأسعار التاريخية، وتجنب الأرقام العشرية العائمة في الحسابات المالية.
4. تفعيل سجل تدقيق موثوق وغير قابل للتعديل من العملاء، مع نسخ خارجية محمية.
5. إضافة اختبارات تحقق خاصة بعزل المستأجرين: مصنع أ لا يستطيع قراءة أو تعديل طلبات مصنع ب، بما في ذلك عبر تحديث factory_id.
6. اختبار roles: viewer للقراءة، sales للطلبات فقط، accountant للمالية، وowner/admin لإدارة الموردين.
7. منع التكرار في إدخال الطلبات والمعاملات باستخدام مفاتيح idempotency ومراجع ثابتة.
8. مراجعة سياسات Supabase وPostgreSQL ومبدأ أقل صلاحية قبل تطبيق SQL في بيئة حقيقية.
9. استكمال معايير خصوصية البيانات السعودية وتوثيق دور كل طرف والتحكم في مدة الاحتفاظ بالبيانات.

## ملاحظات
- ليس هناك نظام هوية أو OTP موصل حاليًا.
- لا توجد أرقام موثقة للطلب السوقي أو فواتير إلكترونية معتمدة.
- لا تسوق النسخة على أنها نظام ERP متكامل حتى تجتاز اختبارات الفواتير والمحاسبة والمخزون والتدقيق.
