# خرسانة برو | Kharasana Pro

منصة تجمع العملاء وشركات الخرسانة الجاهزة ومناديب المبيعات: يرسل العميل طلب خرسانة
واحدًا، تستقبله الشركات المطابقة في منطقته، ترسل عروض أسعار، يقارن العميل ويقبل
العرض المناسب — دون أن تُكشف بياناته الشخصية لأي شركة قبل قبوله للعرض.

A platform connecting customers, ready-mix concrete companies, and sales
representatives: a customer submits one concrete order, matching companies in
the area receive it and send price quotes, the customer compares and accepts
an offer — and their personal contact details are never revealed to any
company until they accept a quote themselves.

> ⚠️ **هذه نسخة عرض تجريبية (demo).** كل بيانات الشركات والعملاء والطلبات
> الظاهرة في `prisma/seed.ts` بيانات وهمية وغير حقيقية بالكامل (أرقام جوال،
> رقم سجل تجاري تجريبي...). الشعار الظاهر في `public/shugan/logo.png`
> وصور أسطول الخلاطات/المضخات في `public/shugan/*.jpg` أصلية فعلًا (مرفقة من
> المستخدم). **لم تُستخدم صورة شهادة السجل التجاري المرفقة في أي مكان** —
> لا في الكود ولا في المستودع — التزامًا بشرط عدم وضع مستندات حساسة في مستودع
> عام؛ رقم السجل التجاري في بيانات العرض التجريبية رقم وهمي بديل. لا يحتوي
> المستودع على أي مفتاح API — كل ذلك يُقرأ من متغيرات بيئة غير مضمّنة في الكود.
>
> **This is a demo build.** Every company/customer/order record in
> `prisma/seed.ts` is fake placeholder data (fake phone numbers, a fake CR
> number). The logo at `public/shugan/logo.png` and the mixer/pump fleet
> photos under `public/shugan/*.jpg` are real assets supplied by the user.
> **The supplied commercial-register certificate image was deliberately
> NOT used anywhere** — not in code, not committed to the repo — per the
> instruction to keep sensitive company documents out of a public repo. No
> secrets are in this repo, and no API keys are hardcoded — everything
> sensitive is read from environment variables that are never committed.

  `UNIFONIC_APP_SID` و`UNIFONIC_SENDER_ID` لأضيفهما كمتغيرات بيئة على
  Netlify — يفعّل الإرسال الفعلي فورًا دون أي تعديل كود آخر.

  للجوال نفسه؛ بعد إتمامها من طرفكم، تزويدي بالمفاتيح الناتجة (`TWILIO_

## 2. القرارات التقنية | Technical decisions

قرارات اتُّخذت بشكل مستقل لإنجاز نسخة قابلة للتشغيل فعليًا دون توقف لطلب اختيارات:

| القرار | السبب |
|---|---|
| **Next.js 16 + TypeScript + Tailwind v4** | إطار واحد يغطي الواجهة وواجهة API معًا، ويعطي أساسًا نظيفًا لتطبيق جوال لاحق عبر نفس الـ API |
| **Postgres (Neon) بدل SQLite** | بدأ المشروع بـ SQLite (صفر إعداد) والمخطط صُمم أصلًا بدون ميزات خاصة به تحديدًا لسهولة الانتقال لاحقًا. عند طلب النشر على Netlify، تبيّن أن SQLite (ملف محلي) لا يعمل على استضافة serverless (نظام ملفات مؤقت)، فتم التحويل الفعلي إلى Postgres عبر Neon و`@prisma/adapter-neon` (اتصال HTTP/WebSocket مناسب لبيئات serverless بدل TCP طويل العمر) |
| **الحالات كنصوص (strings) بدل enum** | قيد فرضته SQLite، مع مصدر حقيقة واحد بالأنواع في `lib/enums.ts` يستخدمه الكود والتحقق (zod) |
| **JWT في كوكيز httpOnly بدل جلسات DB** | كافٍ لهذا النطاق، بلا اعتمادية إضافية. يمكن إضافة جدول Session لاحقًا لدعم إبطال الجلسات عن بُعد |
| **next-intl لتعدد اللغات** | يدعم Next.js 16 رسميًا، ويعطي مسارات `/ar` و `/en` منفصلة مع RTL/LTR تلقائي |
| **هوية خرسانة برو مستقلة (كهرماني/فحمي) عن أزرق شغن** | تنفيذًا لصريح الطلب: هوية عامة للمنصة، وهوية شغن الزرقاء تظهر فقط داخل بطاقة المورد |
| **شعار شغن وصور الأسطول حقيقية** | بعد رفع المستخدم للشعار وكتالوج الشركة، استُبدل البديل النصي بالشعار الفعلي (مقصوص ومنظّف من الإطار الأسود)، وأُضيفت 4 صور حقيقية لمضخات وخلاطات خرسانة مستخرجة من الكتالوج المرفق كمعرض "أسطول الخلاطات والمضخات" أسفل بطاقة شغن. حُجم العرض بقياس بطاقات معرض صغيرة/متوسطة وليس كخلفية بطولية كبيرة، لأن دقة الصور المصدرية متواضعة (~600px) |
| **استبعاد صورة السجل التجاري بالكامل** | المستخدم رفع أيضًا صورة شهادة سجل تجاري حقيقية تحمل رقمًا رسميًا فعليًا. لم تُستخدم هذه الصورة ولا رقمها في أي مكان (لا في الواجهة ولا في بيانات العرض)، التزامًا بشرط "لا تستخدم بيانات أو مستندات الشركة الحساسة داخل مستودع عام" الوارد في الطلب الأصلي |
| **حاسبة الخرسانة: حجم مستطيل بسيط** | طول × عرض × سماكة(سم)/100 × (1 + نسبة هدر%) — الحالة الأكثر شيوعًا (بلاطة/قاعدة)، دون تعقيد زائد بأشكال إضافية غير مطلوبة صراحة |
| **عمولة واحدة لكل عرض مقبول (لا عمولتان منفصلتان)** | المخطط يربط `Commission` بـ `Quote` بعلاقة واحد-لواحد. عند القبول تُحسب عمولة واحدة من إعداد الشركة إن وُجد وإلا العام (`CommissionSetting`)، وتُربط بالمندوب المُحيل إن وُجد لأغراض تتبّع مستحقاته — بدل تصميم أعقد بعمولتين منفصلتين (منصة + مندوب) لم يكن مطلوبًا صراحة |
| **تعديل العرض بدل إنشاء عروض متعددة** | إذا أرسلت الشركة عرضًا ثم عدّلت السعر قبل رد العميل، يُحدَّث نفس العرض (`PENDING`) بدل إنشاء صف جديد — يبقي واجهة المقارنة عند العميل نظيفة (عرض واحد لكل شركة كحد أقصى ما لم يُرفض) |

## 3. التشغيل محليًا | Running locally

### المتطلبات | Requirements

- Node.js 20+ (تم الاختبار على Node 22)
- npm
- قاعدة بيانات Postgres (نستخدم [Neon](https://neon.tech) — طبقة مجانية كافية للتطوير/العرض)

### خطوات التثبيت | Setup

```bash
npm install

cp .env.example .env
# ضع رابط اتصال Postgres الحقيقي (من Neon مثلًا) في DATABASE_URL
# وولّد قيمة عشوائية حقيقية لـ AUTH_SECRET قبل أي بيئة غير محلية:
# openssl rand -base64 48

npm run db:migrate   # ينشئ الجداول على قاعدة البيانات بحسب المخطط
npm run db:seed      # يزرع بيانات شغن التجريبية + المدن + حساب الإدارة

npm run dev
```

افتح http://localhost:3000 — سيُعاد توجيهك تلقائيًا إلى `/ar`.

> منذ الإصدار الثاني، قاعدة البيانات **Postgres في كل بيئة** (محليًا وفي
> الإنتاج) — لم تعد SQLite مستخدمة، لأن استضافات serverless مثل Netlify
> Functions لا تحافظ على ملف SQLite بين الطلبات (نظام ملفات مؤقت/للقراءة
> فقط)، فتفشل عمليات الكتابة (تسجيل، OTP، إنشاء طلب) في الإنتاج. الاتصال
> بقاعدة Postgres يتم عبر `@prisma/adapter-neon` (بروتوكول HTTP/WebSocket
> مناسب للبيئات اللاخادمية، بلا اتصالات TCP طويلة العمر).

| الإدارة | `admin@kharasanapro.demo` / `Admin@12345` عبر `/ar/admin/login` |
| شركة شغن (معتمدة) | جوال `0500000001` عبر `/ar/auth/login` — اختر "شركة خرسانة" |
| شركة بانتظار الاعتماد | جوال `0500000002` |
| مندوب معتمد | جوال `0500000003` |
| عميل تجريبي (له طلب سابق) | جوال `0500000009` |
| أي رقم جديد | يُنشئ حسابًا جديدًا تلقائيًا بعد إدخال الاسم |

**رمز التحقق (OTP) في وضع التطوير:** لا يوجد مزوّد SMS حقيقي متصل بعد، لذلك
الكود يظهر في استجابة الـ API (`devCode`) وفي واجهة تسجيل الدخول نفسها، وأيضًا
مطبوعًا في الطرفية التي تشغّل `npm run dev`. هذا السلوك يُعطَّل تلقائيًا في
الإنتاج (`NODE_ENV=production`).

## 3.1 النشر على Netlify | Deploying to Netlify

المشروع مهيّأ للنشر على Netlify عبر `netlify.toml` وحزمة `@netlify/plugin-nextjs`
(مضافة كـ devDependency، تُفعَّل تلقائيًا من الملف). أسهل طريقة:

1. اربط المستودع (هذا الفرع) بموقع Netlify جديد من لوحة Netlify مباشرة
   ("Import from Git") — هذا لا يحتاج مشاركة أي بيانات دخول معي.
2. من إعدادات الموقع في Netlify → **Environment variables**، أضف:
   - `DATABASE_URL` = رابط اتصال Postgres (Neon) — **استخدم رابط "Pooled
     connection" إن توفر**، لأن دوال Netlify قصيرة العمر ولا تستفيد من اتصال
     مباشر طويل.
   - `AUTH_SECRET` = قيمة عشوائية طويلة (`openssl rand -base64 48`) —
     **مختلفة عن أي قيمة تطوير محلية**.
3. أول عملية `npm install` على Netlify تُشغّل `prisma generate` تلقائيًا
   (عبر `postinstall`)، ثم `npm run build` يبني المشروع.
4. **مهم:** الجداول لا تُنشأ تلقائيًا عند النشر. شغّل الترحيل مرة واحدة قبل
   أول نشر (من جهاز فيه اتصال شبكة عادي بـ Neon):
   ```bash
   npm run db:deploy   # prisma migrate deploy — ينشئ الجداول على قاعدة الإنتاج
   npm run db:seed     # اختياري: بيانات شغن التجريبية على قاعدة الإنتاج
   ```

> **تم النشر فعليًا والتحقق منه على الإنتاج** (بالتعاون مع المستخدم، عبر
> واجهة Netlify نفسها — بيئة التنفيذ الخاصة بي مقيّدة الشبكة ولا تصل إلى
> Neon أو Netlify مباشرة، انظر تفصيل ذلك أدناه). النتيجة: تسجيل دخول
> الإدارة نجح على الرابط المنشور وعرض أرقامًا حقيقية من قاعدة Neon (2
> شركات، عميل، طلب، مندوب) — يثبت أن الاتصال والبناء والمصادقة تعمل فعليًا
> في الإنتاج لا في التطوير المحلي فقط.
>
> **قيد شبكي واجهته أثناء الإعداد:** بيئة تنفيذي لا تصل مباشرة لا لمنفذ
> Postgres (5432) ولا لواجهة Neon HTTP API (كلاهما محجوب على مستوى سياسة
> الشبكة). لذلك تعذّر عليّ تشغيل `prisma migrate deploy` مباشرة على قاعدة
> Neon الحقيقية. الحل: ولّدت SQL الترحيل والبيانات التجريبية محليًا،
> وتحققت من صحتها بالكامل (تشغيل فعلي + `prisma migrate status` يؤكد
> "up to date") على نسخة PostgreSQL محلية داخل بيئتي، ثم زوّدت المستخدم
> بها ليشغّلها بنفسه عبر Neon SQL Editor — وهذا ما حدث بالفعل.

## 4. كيف تم اختباره فعليًا | How this was actually verified

لم يُفترض أن أي شيء يعمل — تم تشغيله والتحقق منه في هذه الجلسة:

- `npx tsc --noEmit` بدون أخطاء.
- `npm run lint` بدون أخطاء أو تحذيرات.
- `npm run build` ينتج بناء إنتاج ناجح لكل المسارات.
- خادم تطوير فعلي + طلبات `curl` حقيقية: طلب OTP → تحقق → إنشاء جلسة →
  إنشاء طلب خرسانة → تأكيد وصول إشعار "طلب جديد مطابق" لحساب شركة شغن **بدون**
  اسم أو جوال العميل في نص الإشعار (تحقق مباشر من قاعدة البيانات).
- تصفح فعلي بمتصفح Chromium (Playwright) على قياس جوال (390×844): تسجيل
  حساب عميل جديد كامل عبر الواجهة، فتح حاسبة الخرسانة وحساب كمية `9.45 m³`
  من أبعاد 10×6×0.15م مع هدر 5% (تحقق يدوي من صحة المعادلة)، تطبيقها تلقائيًا
  في حقل الكمية، إتمام إرسال الطلب ورؤية شاشة النجاح مع رقم الطلب.
  - **تم اكتشاف وإصلاح خلل حقيقي أثناء هذا الاختبار:** حقل الكمية كان
    `step="0.1"` فرفض المتصفح قيمة الحاسبة ذات المنزلتين العشريتين (`9.45`)
    ويمنع الإرسال بصمت. تم تغييره إلى `step="0.01"`.
- تسجيل دخول الإدارة وعرض لوحة بأرقام حقيقية من قاعدة البيانات (عدد العملاء/
  الشركات/الطلبات).
- فحص عربي (RTL) وإنجليزي (LTR) بصريًا للصفحة الرئيسية على قياس جوال، والتأكد
  من انعكاس اتجاه زر واتساب الثابت تلقائيًا بين الجهتين.
- **دورة الطلب ↔ العرض ↔ القبول كاملة**، عبر curl ومتصفح فعلي معًا: عميل جديد
  ينشئ طلبًا → شركة شغن تسجّل دخول وتشوفه ضمن "الطلبات المطابقة لمنطقتك"
  (بدون أي بيانات عميل) → ترسل عرض سعر عبر النموذج → العميل يفتح تفاصيل
  الطلب ويشوف العرض مرتبًا مع تقييم الشركة → يقبله بعد رسالة تأكيد صريحة.
  تحقّق مباشر من قاعدة البيانات بعد القبول أكّد: حالة الطلب/العرض `ACCEPTED`،
  إنشاء سجل عمولة تلقائي (`PER_M3 × 30 = 150 ر.س` مطابق لإعداد العمولة
  الافتراضي)، وأهم نقطة — إشعار شركة شغن يحتوي الآن اسم العميل الحقيقي
  ورقم جواله لأول مرة، بينما أي استجابة API قبل القبول لم تحتوِ عليهما إطلاقًا.
- **نُشر فعليًا على Netlify وتحقّقت من الإنتاج مباشرة**: تسجيل دخول الإدارة
  على الرابط المنشور يعرض أرقامًا حقيقية من قاعدة Neon — يثبت أن الاتصال
  والبناء يعملان على الإنتاج لا في بيئة التطوير فقط (تفاصيل القيد الشبكي
  الذي واجهته وكيف تم تجاوزه موثقة في قسم النشر أعلاه).
- **تتبّع الإحالة**: زيارة `/ar?ref=KP-DEMO001` تحقق منها فعليًا عبر
  `curl -D -` أن كوكي `kp_ref` (httpOnly، 30 يومًا) يُضاف للاستجابة. عميل
  جديد بهذا الكوكي أنشأ طلبًا حقيقيًا وتأكّد من استجابة الـ API أن
  `referredByRepId` مربوط بالمندوب الصحيح تلقائيًا. بعد قبول عرض شغن على هذا
  الطلب (12 م³ × 5 ر.س/م³)، لوحة `/rep` عرضت فعليًا "عمولات معلّقة: 60 ر.س"
  والطلب في القائمة — رقم مطابق حسابيًا.
- **رفع مستند السجل التجاري**: تسجيل شركة جديدة عبر curl مع صورة PNG حقيقية
  (base64) أكّد أن `Company.crDocUrl` في قاعدة البيانات صار `data:image/png;
  base64,...` فعليًا، وتصفّح فعلي (Playwright) للوحة اعتماد الإدارة أكّد ظهور
  رابط "عرض مستند السجل التجاري" بنفس محتوى الصورة المرفوعة.
- **مزوّدات الإشعارات الحقيقية**: تأكدتُ أن غياب متغيرات `TWILIO_*`/`RESEND_*`
  يُبقي السلوك الحالي (console.log) يعمل دون كسر أي تدفق OTP/إشعار قائم —
  التبديل لمزوّد حقيقي فعليًا يحتاج فقط إضافة تلك المتغيرات في بيئة الإنتاج.
- **مجموعة اختبارات Vitest**: `npm test` ينفّذ 43 اختبارًا (8 ملفات) لمنطق
  العمولة، الـ slug، تطبيع الجوال، اختيار/استدعاء مزوّد Unifonic، ومخططات
  Zod — كلها تمر بنجاح (`Test Files 8 passed`, `Tests 43 passed`).
- بعد كل تعديل في هذه الدفعة: أُعيد تشغيل `npm run lint`، `npx tsc --noEmit`،
  و`npm run build` وكلها بلا أخطاء، وتم اختبار التدفقات أعلاه فعليًا على نسخة
  PostgreSQL محلية حقيقية (لا افتراضات) قبل إعادة الإعدادات لقاعدة Neon
  الإنتاجية.

## 5. الأمان والخصوصية | Security & privacy notes

- لا مفاتيح API داخل الكود — كل شيء عبر `process.env`، و`.env` مستثنى من Git
  (`.env.example` فقط هو المُوثَّق).
- `AUTH_SECRET` الافتراضي في `.env.example` **غير آمن عمدًا** ومخصص للتطوير
  فقط — يرفض الكود العمل بدونه في `NODE_ENV=production`.
- كلمات مرور الإدارة مخزّنة بـ bcrypt، لا نص صريح.
- كل رقم جوال/بريد/سجل تجاري في `prisma/seed.ts` وهمي وغير حقيقي.
- استجابات API للطلبات لا تتضمن اسم أو رقم جوال العميل عند إشعار الشركات —
  تحقق فعلي في قسم "كيف تم اختباره" أعلاه.
